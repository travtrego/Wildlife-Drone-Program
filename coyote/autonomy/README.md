# Coyote companion-side autonomy

Jetson-side code that **requests** mission actions. PX4/Pixhawk keeps stabilization, geofence, battery and link-loss failsafes, RTL and pilot override.

## `telemetry.py`

Dependency-free adapter between per-stream PX4 telemetry (as MAVSDK delivers it) and the gate. `TelemetryTracker` takes flight mode, armed, in-air, relative altitude and battery updates with monotonic timestamps and builds one `VehicleSnapshot`. Each stream has its own staleness limit (placeholders sized from the [2026-11-01 SITL observation](../../docs/SITL_VALIDATION_2026-11-01_FAILURE_PATHS.md): mode/armed/in-air 2.5 s at 1 Hz, position 1 s at ~50 Hz, battery 4 s at ~0.6 Hz). While all are within their limits, `telemetry_age_s` is the age of the newest update (link liveness); a stream past its limit makes the snapshot report that stale age, so the authority revokes. A missing or malformed stream makes the age infinite (rejected). The earlier oldest-stream rule revoked every grant within a second in SITL because battery arrives only every ~1.7 s. MAVSDK 3.x `remaining_percent` (0–100) is converted to the gate's 0.0–1.0 fraction here; out-of-range or non-finite values become unknown, never clamped. Out-of-order updates are dropped. `failsafe_active` is a separate input (candidate source: `failsafe_source.py`): until something reports it, or once it is older than 1 s (placeholder), it is `None` and the delegation authority refuses or revokes. `observe_vehicle` / `evaluate_companion_request` chain tracker → `DelegationAuthority` → `evaluate_request`; they send nothing to PX4.

Evidence status: **unit-tested only** (`tests/test_coyote_telemetry.py`) against plain values and a stand-in enum; no MAVSDK subscription task, SITL, bench or flight testing exists.

## `vehicle_link.py`

Connects the pieces above to MAVSDK and a clock. `subscribe_vehicle_telemetry` starts one **read-only** task per MAVSDK 3.x stream (flight mode, armed, in-air, position `relative_altitude_m`, battery `remaining_percent`) feeding `TelemetryTracker`; a stream that ends or raises is recorded in `stream_errors` and stops updating, so it goes stale at its own limit and the authority revokes. `watch_step` / `run_delegation_watch` run the periodic R6 tick: observe the vehicle (which revokes on a silent link even when no companion request is pending), move alerts into `GroundAlertOutbox`, then make at most one send attempt bounded by `send_timeout_s`. Observing comes before sending, so a slow ground link delays an alert, never a revocation. `mavsdk_status_text_sender` maps alert severity by name onto MAVSDK `server_utility.StatusTextType` (names checked against MAVSDK-Python 3.17.2 without a vehicle). Nothing here arms, takes off or changes mode; the only outbound traffic is a STATUSTEXT line.

`WatchConfig` defaults (0.2 s tick, 1 s send timeout) are **model inputs / development placeholders**. The `failsafe_active` source is supplied separately by `failsafe_source.py` (candidate, unobserved). The grant command transport has a candidate in `grant_transport.py`.

Evidence status: **unit-tested only** (`tests/test_coyote_vehicle_link.py`) with fake streams, clocks and senders. Not run against PX4 SITL: stream rates, whether a companion STATUSTEXT reaches and is shown by QGroundControl, and revocation latency on a real link are unobserved.

## `failsafe_source.py`

**Candidate** source for `failsafe_active`, so that R6 grants become possible in SITL (until now nothing supplied it and every grant was refused). It reads PX4 `HEARTBEAT.system_status` through the MAVSDK 3.x `mavlink_direct` plugin (read-only subscription; `MavlinkMessage` field names checked against MAVSDK-Python 3.17.2 without a vehicle). Mapping, chosen conservatively: `STANDBY`/`ACTIVE` → no failsafe; `CRITICAL`/`EMERGENCY`/`FLIGHT_TERMINATION` → failsafe; `UNINIT`/`BOOT`/`CALIBRATING`/`POWEROFF`, unrecognised values, malformed JSON or a non-PX4 autopilot → unknown (refuse/revoke). Only heartbeats from the configured autopilot system/component id (`HeartbeatSourceConfig`, PX4 defaults 1/1, **model inputs**) count, so a ground-station, companion or gimbal heartbeat cannot clear a failsafe. Because PX4 sends HEARTBEAT at about 1 Hz, use `HEARTBEAT_TRACKER_CONFIG` (2.5 s failsafe age, placeholder); the default 1 s would revoke on a slightly late heartbeat. Link loss is still caught at 1 s by the other streams.

**Observed once in PX4 SITL** ([2026-11-01 record](../../docs/SITL_VALIDATION_2026-11-01_FAILURE_PATHS.md), PX4 `6041c961`): HEARTBEAT at 1 Hz from (1, 1) only, integer enum fields, `system_status` 3 disarmed, 4 armed, **5 during a GPS-loss failsafe**, and 0 (mapped to unknown) on the ground while preflight checks failed afterwards. One session, one PX4 build; other failsafe types not observed. This is defence in depth: failsafe actions that change mode (RTL/LAND) already revoke through the flight-mode stream.

Evidence status: **unit-tested only** (`tests/test_coyote_failsafe_source.py`) with fake messages and clocks.

## `grant_transport.py`

**Candidate** transport for the R6 grant/revoke command, replacing the SITL watch script's keyboard stand-in once wired. The ground station sends a MAVLink `COMMAND_LONG` to the companion component: command `MAV_CMD_USER_1` (31010), `param1` = 1 grant / 2 revoke (anything else, including 0, is rejected), `param2` = grant sequence, a whole number 1..2^24 that the ground tool must increment on every grant. Only commands from the configured ground station (default 255/190) addressed to the configured companion (default 1/191) are honoured; a wrong source or target, broadcast, bad action or bad sequence is logged as `REJECTED` and never touches delegation state. All ids are **model inputs** (MAVLink conventions, not Coyote parameters). A decoded grant goes through `DelegationAuthority.request_grant`, so every existing refusal rule still applies; the companion's receive time is used as `issued_at_s` because there is no shared clock, so the 2 s grant-age check only bounds local delay and replay protection rests on the sequence rule. `pump_ground_commands` subscribes read-only to `mavlink_direct` `COMMAND_LONG`; if that stream ends or raises, the operator can no longer revoke through it, so delegation is revoked with the new reason `COMMAND_LINK_LOST` (`COYOTE AUTONOMY OFF: GROUND CMD LINK LOST`, WARNING). No `COMMAND_ACK` is sent yet; a retransmitted grant reuses its sequence and is refused without changing state.

Evidence status: **unit-tested only** (`tests/test_coyote_grant_transport.py`) with fake messages, streams and clocks. Not observed: whether PX4 forwards a ground-station `COMMAND_LONG` to the companion link, whether MAVSDK `mavlink_direct` delivers it (or MAVSDK answers it itself), and whether a ground-side sender's commands reach the companion. Ground tool (owner decision 2026-11-06): a ground-side script/app that increments the sequence on every grant, not a fixed QGroundControl button; its deterministic part is [`coyote/ground/grant_sender.py`](../ground/README.md).

## `delegation.py`

Deterministic state machine that produces the gate's `operator_delegated` flag from R6 (owner decision 2026-10-18; see [DECISIONS.md](../DECISIONS.md) once PR #9 merges). A ground-station grant (with a strictly increasing sequence number, at most 2 s old) is accepted on the ground before takeoff (owner decision 2026-10-20) or in the air, while the latest observation is fresh, failsafe-free and not in a pilot or PX4 recovery mode. A ground grant never lets the companion arm. Once the operator has armed, the gate allows a companion `TAKEOFF` request (owner decision 2026-10-20, option 1); every other request still requires armed and airborne. Any PX4 failsafe, unknown failsafe state, telemetry/observation gap over 1 s, pilot mode, RTL/LAND, disarm after the grant, landing after flying under the grant, bad clock or operator revoke clears it, so one grant covers at most one flight. Revocation is sticky: only a new grant restores it. Each revocation queues one `RevocationAlert` (reason, detail, time) for the ground station; delivery is the future adapter's job.

Evidence status: **unit-tested only** (`tests/test_coyote_delegation.py`). The 1 s / 2 s timings are development placeholders. `failsafe_active` and the grant command have candidate sources (`failsafe_source.py`, `grant_transport.py`); losing the grant command stream revokes with `COMMAND_LINK_LOST`. No bench or flight testing exists.

## `ground_alerts.py`

R6 requires the ground station to tell the operator, with the reason, whenever delegation is revoked. `DelegationAuthority.drain_alerts()` empties its queue, and revocations cluster around link failures, so draining straight into a send that fails would lose the alert. `GroundAlertOutbox` takes drained alerts and keeps each one, in revocation order, until the sender reports success; a failed send (False or an exception) leaves it at the head and waits `retry_interval_s` (placeholder 0.5 s) before retrying. The queue is bounded (`max_pending`, placeholder 16): overflow drops the oldest alert not currently being sent and sends a "N AUTONOMY ALERTS DROPPED" line first, so loss is visible. `format_status_text` produces an ASCII line of at most 50 characters (MAVLink `STATUSTEXT` size) such as `COYOTE AUTONOMY OFF: PX4 TELEMETRY LOST`, with a severity whose names match MAVSDK `server_utility.StatusTextType` (PX4 failsafe CRITICAL; operator revoke NOTICE; end of flight INFO; everything else WARNING). The full `detail` string stays in the local record. Transport is injected: `deliver(send, now)` for a synchronous sender, or `next_message` / `mark_sent` / `mark_failed` for an async MAVSDK task. "Sent" means the transport accepted it, not that the operator saw it; no ground-station acknowledgement is defined. Delivering an alert never restores delegation.

Evidence status: **unit-tested only** (`tests/test_coyote_ground_alerts.py`). STATUSTEXT as the delivery path is an implementation choice; whether QGroundControl shows a companion-originated STATUSTEXT, and from which MAVLink component, is not observed. No MAVSDK task, SITL, bench or flight testing exists.

## `action_gate.py`

Deterministic, dependency-free gate that decides whether the companion computer may forward a proposed action (`HOLD`, `GOTO_LOCAL`, `RETURN_TO_LAUNCH`, `LAND`) to PX4, given the latest telemetry snapshot. Checks run in a fixed order:

1. Stale or invalid telemetry → reject everything (PX4 link-loss failsafe owns the aircraft).
2. Pilot-controlled PX4 mode (`MANUAL`, `STABILIZED`, `ALTCTL`, `POSCTL`, `ACRO`, `RATTITUDE`) → reject everything; the companion yields.
3. PX4 recovery mode (`RETURN_TO_LAUNCH`, `LAND`) → reject everything; never fight RTL or a failsafe.
4. Mode not in `HOLD`/`MISSION`/`OFFBOARD`, or no explicit operator delegation → reject.
5. `TAKEOFF` (owner decision 2026-10-20, operator on site): allowed only when armed by the operator, on the ground, delegated, in `HOLD`/`MISSION`, battery known and at or above the takeoff reserve (placeholder 80%), and climb altitude inside the advisory limits. The companion never arms; there is no arm action.
6. Any other action when not armed and airborne → reject.
7. De-escalating actions (`HOLD`, `RETURN_TO_LAUNCH`, `LAND`) → allow.
8. `GOTO_LOCAL` → allow only inside the advisory altitude band and home radius and above the advisory battery reserve (battery must be a 0.0–1.0 fraction; values outside that range, such as MAVSDK's 0–100 percent passed straight in, are rejected); otherwise reject with a *recommended* action (`HOLD` or `RETURN_TO_LAUNCH`) that the gate never issues itself.

### Evidence status

- **Unit-tested only** (`tests/test_coyote_action_gate.py`). Not yet wired to MAVSDK, not run in PX4 SITL, not bench- or flight-tested.
- `AdvisoryLimits` defaults (60 m ceiling, 5 m floor, 150 m radius, 40 % goto reserve, 80 % takeoff reserve, 1 s telemetry age) are **model inputs / development placeholders**, not a validated Coyote envelope. They must be configured inside, never looser than, the PX4 geofence and battery failsafe parameters.
- `operator_delegated` will be sourced from a **ground-station command** (owner decision 2026-10-18, [R6](../DECISIONS.md)). The future MAVSDK adapter must clear it on any PX4 failsafe, telemetry-link loss or pilot takeover, require the operator to re-send the command, and notify the ground station with the reason. Not implemented yet. PX4 flight mode alone cannot prove delegation — for example `HOLD` can be pilot- or failsafe-selected.
- This gate does not implement wildlife stand-off distances, obstacle avoidance or animal identification.
